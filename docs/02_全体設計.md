# STEP 2 全体設計

> このリポジトリは公開設定のため、本書には氏名・金額・カード番号などの実データを記載しない。
> 実データ（メンバー一覧・単価表・カード対応表）は本番環境で管理画面から登録する。

## 1. システム構成

| 項目 | 採用 | 理由 |
|---|---|---|
| フレームワーク | Django 5.2（LTS） | ログイン・権限・管理画面・CSRF対策・マイグレーションが標準で揃う |
| データベース | PostgreSQL 16 | 確定済みデータの保護を DB トリガーでも行える。同時更新に強い |
| 画面 | Django テンプレート（サーバー描画）＋必要箇所のみ JavaScript | 保守が容易。給与・経費は描画前にサーバーで認証を確認 |
| PDF | WeasyPrint＋Noto Sans JP（フォントを同梱） | A4・日本語の文字化け防止 |
| シフト画像 | Pillow（サーバーで PNG 生成）＋ブラウザの画像コピー機能 | 誰の端末でも同じ見た目・高解像度 |
| 資料取り込み | openpyxl / xlrd / csv / pdfplumber / Tesseract（日本語 OCR） | Excel・CSV・PDF・画像PDF に対応 |
| Google スプレッドシート | Google Sheets API（任意設定） | 未設定でも Excel・CSV で運用可能 |

### ホスティング（推奨）
**Render**（Webサービス＋マネージド PostgreSQL＋永続ディスク）を推奨する。

- GitHub に push すると自動でデプロイされ、サーバー管理が要らない
- データベースは毎日自動バックアップされる（有料プラン）。復元も管理画面から行える
- アップロードした資料は永続ディスクに保存し、別途日次でバックアップする
- 費用の目安は、小規模構成で月数千円程度
- 注意：日本リージョンがないため、データはシンガポールに保存される。国内保存が必須なら Google Cloud Run（東京）＋Cloud SQL を使う（運用の手間はやや増える）
- Docker で動く構成にしておき、どちらにも移行できるようにする

## 3. データベース設計（主要テーブル）

```
Member ─┬─ MemberAlias（表記揺れ）
        ├─ CardCode（カード識別4桁 → 担当者。16桁の番号は保存しない）
        ├─ MonthlyStandardOverride（月別の出勤基準）
        ├─ ShiftEntry（1人×1日の勤務区分） ──同期──▶ AttendanceDay（予定／実績／状態）
        ├─ PaidLeaveGrant / PaidLeaveRequest / PaidLeaveAdjustment
        ├─ SalesCount（獲得件数・入金確定件数。商材別の内訳も可）       ┐
        ├─ BaseSalary（正社員の基本給の改定履歴）                     │ 給与用の認証
        ├─ PayrollStatement ─┬─ PayrollInput（自動値／修正値）        │
        │                    └─ PayrollLine（支給・控除の行）          │
        └─ ExpenseRecord（自動値／修正値・状態・反映先）               ┘ 経費用の認証
WorkType（出勤換算・有給換算）   RateTable（単価表・有効期間つき）
PayrollItemDefinition（給与項目：区分・計算方法・適用範囲）   Team / TeamMembership
SourceFile（元資料・SHA-256）  ImportProfile（読み取りルール）  ExpenseIssue（エラー・確認事項）
AuditLog（全操作の記録・変更削除不可）
```

### 共通ルール
- **年月**は「その月の1日」の日付で保存する
- **自動値と修正値は別の列**に保存し、修正値があればそれを使う。修正の理由は必須とし、監査ログに前後の値を残す
- 給与画面で数値を直しても、元のシフト・勤怠・営業件数は変更しない
- **確定済みの給与**は、アプリ（モデルの save）と DB トリガーの二重で変更・削除を禁止する。確定時に、計算に使った単価表・項目名・元データをスナップショット（JSON）として保存する
- 確定後に経費などが追加・修正された場合は「要確認」フラグを立てるだけで、金額は自動で変えない。再計算は管理者が明示的に行う
- 退職者は削除しない（`status=retired`）。メンバーの削除は管理画面でもできない
- **監査ログ**は DB トリガーにより UPDATE と DELETE ができない

## 4. データの連携

```
シフト入力 ─▶ 勤怠の予定（未確定の日だけ更新。確定・修正済みの日は上書きしない）
勤怠（前月の実出勤日数）─────────────────┐
営業件数：前月獲得件数・当月入金確定件数 ─┼─▶ 単価判定 ─▶ 営業報酬
資料取り込み ─▶ 経費明細 ─▶ 承認 ──────┼─▶ 給与計算 ─▶ 確定（スナップショット）─▶ 明細PDF
給与項目の設定（固定額・当月のみの項目）─┘      └─ 承認済み経費は「給与反映済み」にして二重反映を防ぐ
```

### 給与計算（既存の「月次計算」シートを再現）
- 単価 = 単価表[前月出勤日数（**小数点以下切り捨て**）][前月獲得件数]（個人事業主とインターンで別の表）
- 営業報酬 = 当月入金確定件数 × 単価
- 差引支給額 = 支給合計 − 控除合計（源泉所得税は差し引かない）
- 前月の出勤日数・獲得件数がない場合は**手入力を必須**とし、未入力のままでは計算・確定できない
- 既存シートとの照合：保存されている計算結果のうち、前月データがそろっている全行で単価・営業報酬・支払総額が一致することを確認済み（実データを使う照合スクリプトはリポジトリ外で管理）

### 給与項目の初期設定（データとして登録。プログラムには書かない）

| 項目 | 区分 | 計算方法 | 対象 |
|---|---|---|---|
| 営業報酬 | 支給 | 入金確定件数×自動単価 | 個人事業主・インターン |
| 商材別報酬（例：プロパン・都市ガス・訪問電気） | 支給 | 商材別件数×単価（都市ガスの単価はその月の電気の単価と同じ） | 個人専用 |
| 交通費 | 支給 | 承認済み交通費 − 35,000円 | 個人事業主（代理店を含む） |
| 交通費 | 支給 | 承認済み交通費 | インターン |
| 立替金 | 支給 | 承認済み立替金 | 全員 |
| 手当・特別手当・その他報酬 | 支給 | 毎月入力 | 全員 |
| インターンリーダー手当 | 支給 | チームメンバーの件数×500円（リーダーが月4日以上出勤した場合） | 個人専用 |
| チーム達成ボーナス | 支給 | チーム平均件数 70/80/90件以上 → メンバー1名あたり 3/4/5万円（100件以上は手入力） | 個人専用 |
| ガソリン代 | 控除 | 承認済みガソリン代（カード識別4桁で振り分け） | 個人事業主 |
| アプリ手数料 | 控除 | 固定 4,000円（毎月） | 個人事業主 |
| ログ機械代金 | 控除 | 固定 5,000円（初回の給与のみ） | 個人事業主（代理店を含む） |

- 正社員は明細を作らない。前月出勤日数・獲得件数・基本給を参照できるようにする（新規正社員は3か月目以降の基本給改定をリマインドする）
- 明細のレイアウトは既存の「明細書 / STATEMENT」を再現する。支払日は月末、対象期間は表示しない

## 5. 権限と追加パスワード認証

| 機能 | ログイン | 追加パスワード |
|---|---|---|
| ダッシュボード・シフト・勤怠・メンバー | 必要 | 不要（給与・経費の金額は表示しない） |
| 給与・報酬（画面・API・CSV・PDF・管理画面） | 必要 | **給与用** |
| 資料・経費（画面・API・ファイル・管理画面） | 必要 | **経費用** |

- **サーバー側で3重に検証**する
  1. ミドルウェアが URL の先頭（`/payroll/` `/api/payroll/` `/admin/payroll/` など）で判定する。新しい画面を追加してデコレーターを付け忘れても守られる
  2. 各ビューのデコレーターでも判定する
  3. 管理画面のモデルは認証前なら空の一覧を返し、autocomplete などの別経路も遮断する
- 認証状態はサーバー側のセッションにだけ持つ。30分操作がないとき、認証から8時間たったとき、ログアウト時は無効になる
- 5回続けて間違えると15分ロックする（設定で変更可能）
- パスワードは Django 標準のハッシュで DB に保存する。ソースコードには書かない
- 初期設定は `python manage.py set_stepup_password --scope payroll`（経費は `--scope expenses`）で行う
- 変更は代表者権限のユーザーだけが「追加パスワードの変更」画面から行える。変更履歴と監査ログを残す
- 給与と経費は独立している。片方の認証で、もう片方は開けない
- 入力の成功・失敗・ロックは監査ログに残す

## 6. シフト表の分析（既存ブック）
- 「シフト入力」シートで、名前ごとに「出勤日」または「休み」を選び、日付を `1,2,3`（`、` `.` `，` も可）の形式で入力する。「シフト表」シートが●を展開して出勤日数を数える
- 出勤と休みの2種類だけで、半日・有給の区分はない → 新システムでは勤務区分を増やす（出勤／半日稼働／休み／有給／半日稼働＋半日有給。管理者が追加できる）
- 既存運用の弱点（新システムでは画面入力にして解消する）
  - `21.22` が数値として保存されると、`21.20` が `21.2` に化けるおそれがある
  - `3.4.5..7` のような入力ミスを検出できない
  - 名前が姓だけで入力されるため、同じ姓の人を区別できない → 別表記（MemberAlias）で対応する
- 過去月の移行用に、旧形式の入力（`出勤日`・`休み`＋日付リスト）を取り込む機能を用意する

## 7. 保留事項（決まるまでは設定で変更できる形にする）
1. インターンの月間出勤基準日数
2. 電気の単価を自動単価としていることの最終確認
3. インターンリーダー手当で数える件数（現在は入金確定件数・リーダー本人を除く）
5. 未入金・不備数の集計（顧客管理シート）は今回は対象外とし、将来追加する

## 8. STEP 3 で決めた運用ルール
- シフトの「前月コピー」は、同じ日付にコピーする。入力済みの日は変更しない。前月にしかない日付（31日など）はコピーしない
- 未入力の日は「未定」とし、休み扱いにしない。曜日や祝日（祝日は表示のみ）で自動的に休みにはしない
- 勤怠の実出勤日数 = 確定・修正済みの実績 ＋ 未確定日の予定。給与の「前月出勤日数」にはこの値を使う。勤怠データが1日もない月は手入力
- 勤怠の月次確定をすると、未確定の日は予定どおりの実績として確定し、その月は変更できなくなる。解除するには理由の入力が必須
- 有給はシフトを予定の元データとする。有給申請を承認すると、シフトに「有給」（半日なら「半日稼働＋半日有給」）が入る
  - 取得済み：勤怠が確定した日
  - 取得予定：未確定の日
  - 申請中：残日数から引かない
- 法定付与は「法定付与を作成」ボタンで登録する（出勤率8割以上の確認は管理者が行う）。付与日を過ぎても登録されていない法定付与は警告を出す
- 既存シフト表からの移行は `python manage.py import_legacy_shift <ファイル> [--apply]` で行う
  - 「出勤日」：入力した日＝出勤、それ以外＝休み。「休み」はその逆
  - 姓だけの名前で同じ姓の人がいる場合や、日付の欠けが疑われる値（21.2 など）はエラーにして、何も取り込まない
  - 実際のシフト表（2026年11月分）で、全12行の出勤日数がシートの計算と一致することを確認済み

## 9. STEP 4 で決めた計算ルール（2026年10月の実データで照合済み）
- プロパンの単価は固定：風呂あり 35,000円、風呂なし 25,000円
- 都市ガス・都市ガス電気・訪問電気の単価は、その月の自動単価（単価表）と同じ。変える場合は「インセンティブ単価」を修正する
- 商材別に報酬を計算する人は、通常の「営業報酬」の対象外にする（給与項目の「対象外にする人」で設定）。この人の入金確定件数は商材別件数の合計とする
- チーム達成ボーナス
  - 平均件数 ＝ リーダーを含むチーム全員の当月入金確定件数の平均
  - 支給額 ＝ 段階の金額 × リーダー以外のメンバー数
  - 平均が100件以上のときは「別途協議」として手入力が必要
- インターンリーダー手当 ＝ チームメンバー（リーダー本人を除く）の当月入金確定件数 × 500円。条件は、リーダーの**当月**の出勤が4日以上
- 交通費は、個人事業主（代理店を含む）が承認済みの交通費 − 35,000円（下限0円）、インターンは承認済みの交通費をそのまま
- ログ機械代金 5,000円は、過去に確定した給与がなく、入社（契約開始）が当月または前月の場合だけ自動で差し引く
- 明細では、0円の行は「常に表示」の項目（営業報酬・交通費精算・手当・ガソリン代・アプリ手数料）だけ表示する
- 照合結果
  - 既存の月次計算シートで前月データがそろっている11行：単価・営業報酬・支払総額がすべて一致
  - 商材別報酬＋チーム達成ボーナスの人の2026年10月の明細：合計金額が一致
  - 照合スクリプトは実データを使うため、リポジトリ外で管理している
- 初期データの登録は `python manage.py import_legacy_payroll_setup <給与計算ブック> --effective-from 2026-01 [--apply]` で行う（メンバーと単価表）

## 10. STEP 5 で決めた資料取り込みのルール（2026年10月の給与と照合済み）
- ガソリン代（ENEOS FC 請求書・画像PDF）
  - 「請求明細表（合計版）」のページから、カードごとの合計を読み取る
  - 担当者は、カード番号の右側の〔R0007〕などの4桁で判定する（末尾の数字では判定しない）
  - カード対応表にないカードは無視する（自動で対象外）
  - 9月分の請求は10月の給与で差し引く（＋1か月）
  - 正社員のカードは「給与に反映しない」設定にして、自動で対象外にする
- OCR の精度
  - カード識別4桁は正しく読める
  - 金額は誤読しやすいため、前処理を変えて3回読み、2回以上一致した値だけを候補として出す
  - OCR で読んだ行は必ず「確認待ち」にする。元資料のページ画像を見比べ、金額を確認・入力してから承認する
- 交通費（請求書PDF）
  - 「交通費(8月分) 氏名 単価 数量 価格」の行だけを読み、それ以外の品目は無視する
  - 8月分は10月の給与に反映する（＋2か月）
  - 個人事業主は承認済みの交通費 − 35,000円を支給する
- 氏名は表記揺れ（空白・全角半角）を吸収し、姓だけでも一人に決まれば振り分ける
  - 「沢」と「澤」のような異体字や、同じ姓が複数いる場合は「確認待ち」にする
  - 管理者が対象者を選ぶときに「別名として登録」すると、次回から自動で振り分ける
- Excel・CSV は、見出し行ごとに読み取りルール（列の対応・経費項目・反映月のずれ）を保存して、次回から自動で使う
  - 見出しが変わった資料は自動で読み替えず、設定画面で確認する
- 同じファイル（SHA-256）は取り込まない
- 取引番号があればそれで、なければ種類・カードまたは氏名・利用日・金額・資料の月・内容で同じ取引を判定する
  - 同じ取引が見つかっても削除はしない（「重複の疑い」を表示するだけ）
- 承認できるのは、確認事項がすべて解決していて、対象者・経費項目・金額・反映月がそろっている行だけ
- 承認済みの行は給与確定時に「給与反映済み」になり、変更できなくなる
- 給与確定後に承認・修正・対象外にした場合は、給与側に「要確認」を立てる（金額は自動で変えない）
- LINE などで別途届いた経費は「氏名 金額（内容）」の文面を貼り付けて取り込む（スクリーンショットを根拠として保存できる）
- アップロードした資料・写真はデータベースに保存する（DB のバックアップで一緒に保全・復元できる）
- 本番サーバーには Tesseract（日本語）と poppler-utils が必要（画像PDFの読み取り用。Dockerfile でインストールする）
